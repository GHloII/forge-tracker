# UI reference

The dictionary of interface terms lives on one page: https://ilyabirman.ru/reference/. Read the live page with your web-fetch tool each time, since entries change. Ask the tool for the entries word for word.

Every observation you make rests on the dictionary: name the term, quote its entry and link to it. The links let the reader check each claim against the source, so an observation is only as strong as the entry behind it.

## Rules

- Use the entry's main term. If the user's word is a variant or slang, name the main term.
- Quote definitions as written and link the entry: `https://ilyabirman.ru/reference/#<id>`.
- Use each term in the sense its entry states. When you add your own interpretation, mark it as yours.
- Link only to addresses that appear on the page.
- If the title of a relevant term is itself a link (usually to an article on ilyabirman.ru or bureau.ru, often bureau.ru/soviet), open that link with your web-fetch tool and read the article before you write the answer, and use what it says in the answer. Do this for every relevant term whose title has a link, whether or not the entry alone seems enough. If a link doesn't open, say so in one sentence and rely on the dictionary entry alone. Exception: for the nine core terms (see «Core terms: article digests» at the end), use the digests instead of opening their articles, unless the live page shows a different title link than the one recorded there, you need an exact quotation, or the digest doesn't cover what the observation needs.
- When a term seems missing, try its variants, the English or Russian equivalent, and a word stem (definitions are inflected: search «загрузк»). If the page looks cut off, fetch the rest.

## Reviewing an interface

1. Check that you have the interface: a screenshot, a screen description, a flow or the URL of a published page (see «Reviewing a published page by URL»). If there's none, ask for it. Otherwise answer right away; if the user or their task is unclear, don't guess and don't state assumptions, just work with what is on screen.
2. A screenshot shows one state, so describe what's visible: layout, labels, grouping, styling. Leave out behaviour you can't see (response to clicks, undo, modes, loading, saving data). Assess sizes and contrast only from exact values.
3. Write concrete observations. Base each one on a dictionary entry, with its quote and link. A thought you can't tie to an entry is left out. Name what you see instead of general impressions such as «сильный» or «удачный».
4. Pick candidates. Go through the nine core terms one by one: Человечность, Сценарий, Ментальная модель, Консистентность, Информативность, Информационный мусор, Обратная связь, Обратимость, Модальность (their digests are at the end of this file). Then look up terms for the specific elements: forms, navigation, loading, popups, gestures, states and so on. A term is a candidate when you already have a concrete observation for it on this screen. Don't open any articles yet.
5. Read the articles. For each candidate outside the nine core terms whose title links to an article, open and read it (see Rules); for the core terms use the digests. If an article changes or removes an observation, revise the candidates. Then report the observations you actually have, up to 10, those that most bear on the user's task first.

Open the answer with exactly this line: «Вот что я заметил исходя из своего понимания справочника:». Then show the marked-up screenshot, if you made one (see «Marking the screenshot»), and the observations. End with the last observation: no summary, no closing sections.

Present the observations as plain description. Don't sort them into problems and strengths, don't label any of them as good or bad, and don't use evaluative words such as «проблема», «ошибка», «хорошо», «удачно». Don't add a section for things beyond the dictionary (assumptions, doubts about the data, behaviour to check, ethics, product hypotheses).

Write each observation as a short paragraph of plain prose, no labels. Start with the term in bold, linked to its entry, and the definition (or the part that bears on the observation) quoted verbatim. Then say in one or two sentences what on screen it refers to. Where the entry implies a concrete action that follows from what is on screen, end with it. If the term's title links to an article, you have read it or used its digest (see Rules): link it in the same paragraph and say what it adds. Quote the article verbatim only if you opened it this time; a digest is a retelling, so introduce it as such («по статье…»). Whenever a point mentions another dictionary term, link it to its entry as well, so the reader can follow every reference.

An example of the whole answer, for format only:

```markdown
Вот что я заметил исходя из своего понимания справочника:

1. **[Подтверждение](https://ilyabirman.ru/reference/#confirmation)** — «Антипаттерн, когда при получении команды опасного действия машина переспрашивает пользователя, уверен ли он, исходя из ошибочного предположения, что увидев вопрос, пользователь снова обдумает решение.» Перед удалением экран показывает диалог «Вы уверены?» с кнопками «Да» и «Отмена», а возможности отменить удаление не видно. Это можно заменить отменой удаления, как описано в [Анду](https://ilyabirman.ru/reference/#undo).

2. **[Близость](https://ilyabirman.ru/reference/#proximity)** — «Закон восприятия, согласно которому объекты, расположенные рядом, кажутся связанными и по смыслу.» Поля «Фамилия», «Имя» и «Отчество» стоят вплотную, а от поля «Телефон» отделены заметным отступом, поэтому читаются как одна группа.
```

## Reviewing a published page by URL

When the user sends the address of a published page, review that one page the same way as a screenshot (same two passes, same answer format), with these differences.

1. Open the URL with your web-fetch tool. Review only that page; open other pages of the site only if the user asks. If the page doesn't open, needs a login, or comes back nearly empty (content drawn by scripts), say so in one sentence and ask for a screenshot instead of guessing.
2. Try to get a screenshot yourself before asking the user for one. Take it in this order, without asking the user first:
   a. If your tool list has a tool that opens a web page in a browser and takes a screenshot, use it.
   b. Otherwise, if you can run shell commands, look for a browser already installed on the user's machine. Never install one. On macOS check `/Applications` for `Google Chrome.app`, `Chromium.app`, `Microsoft Edge.app` or `Brave Browser.app`; elsewhere check `which google-chrome chromium chromium-browser microsoft-edge`. With a Chromium-based browser take the screenshot in headless mode, for example `"<browser binary>" --headless=new --disable-gpu --hide-scrollbars --window-size=1440,5000 --virtual-time-budget=15000 --screenshot=<scratch dir>/page.png <URL>`. Save the file in a scratch directory, not in the project. Firefox also works headless (`firefox --headless --screenshot <file> <URL>`). The binary on macOS is inside the app: `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`.
   c. Open the image and look at it. Know the limits of such a capture: it is one state at one width (1440 px by default); a page taller than the window is cut off, so say which part you saw and take more of it with a taller window or crops if the observations need it; images that load lazily may come out as empty blocks, so don't assess those blocks; the site may show a region or cookie banner. If it matters, say so in the answer.
   d. If the screenshot works, review it as a screenshot (see «Reviewing an interface», «Marking the screenshot»): then points 3 and 5 below no longer limit you, and you don't add the sentence from point 4. Say in the answer which state and screen width the screenshot shows.
   e. If it doesn't work, say in one plain sentence exactly why, and go on with the text and structure of the page, asking for a screenshot as point 4 says. The reasons you may name: there is no tool that takes screenshots and no shell; no installed browser was found (say «Chrome или другой браузер на этом компьютере не найден»); the browser started but the capture failed or came back empty (give the short error). Don't guess a reason you haven't checked.
   Python image libraries (Pillow) may live in the user's site-packages; if you run Python with `-I` for safety they won't import, so run it without `-I` from a directory that is not the downloads folder, and pass file paths as arguments.
3. Without a screenshot, the fetch gives you the text and structure of the page, not its rendering. What you have: headings and their order, text, link and button labels, form fields and their labels and placeholders, navigation items, alt texts, what is linked where. What you don't have: layout, spacing, grouping by distance, colours, contrast, sizes, how icons and images look, hover and focus states, animation, behaviour on a phone. Write nothing about what you don't have, and don't infer it from class names or markup.
4. So the observations rest on what text and structure show: what a visitor can do on the page and in what order (Сценарий), what share of the text carries meaning (Информативность), what the page makes the person do that a machine could (Человечность), whether the same things are named and phrased the same way (Консистентность), how forms, navigation, labels and messages are built, and so on. Terms about appearance (Близость, Информационный мусор, Вибрация, Аффорданс and the like) are out unless there is a screenshot, whether the user's or yours; with a screenshot, use both it and the text. After the opening line, add one plain sentence saying that you saw only the text and structure of the page, not its appearance, so the observations don't cover how it looks, and asking the user to send a screenshot of the page (the whole page, or the screens that matter most) so that you can assess the appearance too. Put the request there, not at the end: the answer still ends with the last observation. Don't mark up a picture when there is none.
5. Refer to a part of the page by its visible heading or label text (keep quotations of the page's own text short), so the reader can find it.

## Marking the screenshot

When the interface is a screenshot and you can run code, mark the observations on a copy of it, so the reader sees exactly which element each observation is about.

1. Number the observations (1, 2, 3…) and start each one with its number: «1. **[Подтверждение](…)** — …». An observation about the screen as a whole gets no number.
2. Visually select each observed element on the image and label it with its number, keeping the element itself readable.
3. Open the marked-up image and check that every selection and number points to the right element. Fix any that are off, then check again.
4. Show the image right after the opening line, before the observations. Use one neutral colour for all selections.

## Core terms: article digests

Checked on 27.10.2026. These are retellings in plain words, not quotations, so use them as a retelling and never as a verbatim quote. Definitions are not cached here: always quote them from the live dictionary page. If the live page shows a different title link for one of these terms than the one below, open the new link and read it.

1. **Человечность** — entry: https://ilyabirman.ru/reference/#humaneness · article «Как сделать интерфейс дружелюбным?»: https://bureau.ru/soviet/20150714/
   Интерфейс подстраивают под человека с его слабостями (забывчивость, путаница лево/право, ошибки раскладки), а не человека под интерфейс. Примеры из статьи: форма не должна сообщать «не заполнено одно или несколько полей», раз машина знает, какие именно; опрос не должен требовать подбирать проценты так, чтобы вышло 100; в магазине джинсов человек выбирает размер в привычной системе, а пересчёт идёт за кулисами. Отсюда принцип «пусть потеет машина»: не заставлять человека считать в уме, помнить путь к файлу, сверять длинные коды.

2. **Сценарий** — entry: https://ilyabirman.ru/reference/#scenario · article «Как составлять пользовательские сценарии»: https://bureau.ru/soviet/20260825/
   Сценарием часто ошибочно называют последовательность макетов, состояние экрана или нажатие кнопки; это не сценарии. Сценарий описывает то, что происходит в реальности человека: с какими мыслями, ожиданиями, ограничениями и данными он пришёл, какую задачу решает. Сценарии предшествуют проектированию и не «получаются» в его ходе. Писать их нужно на языке предметной области, без слов «кнопка», «окно», «экран», «режим»: если они есть, это описание интерфейса. Реакции системы, ошибки и лоадеры в сценарий не входят, им место в документации к макетам. Вариации оформляют как подсценарии внутри основного. Роли пользователей описывают отдельно; вымышленные персоны с биографиями автор считает бесполезными. Если сценариев слишком много, границу проводят по смыслу продукта вместе с клиентом.

3. **Ментальная модель** — entry: https://ilyabirman.ru/reference/#mental-model · в заголовке нет ссылки на статью, достаточно статьи словаря.

4. **Консистентность** — entry: https://ilyabirman.ru/reference/#consistency · в заголовке нет ссылки на статью, достаточно статьи словаря.

5. **Информативность** — entry: https://ilyabirman.ru/reference/#informativeness · article «Какие ещё есть способы повысить информативность?»: https://bureau.ru/bb/soviet/20160809/
   Информативность — доля смысловой части в общей длине сообщения; канал ограничен, поэтому высокая информативность признак хорошего интерфейса. Повысить её можно двумя способами: добавить сигнал или убрать шум. Статья о втором: убрать лишнее (рамки, тени, текстуры, повторяющиеся детали пиктограмм, ссылки в «градуснике», дублирующие главное меню и заголовок страницы) и вынести за скобки повторяющееся (общий заголовок списка вместо повторов одного слова, повторяющийся месяц в колонке дат). Автор замечает, что когда лишнее убрано, встаёт вопрос, зачем на сайте такая сложная иерархия.

6. **Информационный мусор** — entry: https://ilyabirman.ru/reference/#noise · article «Что не так с чересполосицей?»: https://bureau.ru/bb/soviet/20171114/
   Чересполосица — информационный мусор. Любой нарисованный графический элемент порождает элементы, которых не рисовали (эффект «1 + 1 = 3 или больше»): две тёмные полосы дают три полосы с белой между ними. Когда полос много, они вибрируют в глазах, сбивают со счёта, и уже не понять, что цвет, а что фон; это эффект регулярной структуры, от которой нужно избавляться. Снижение контраста делает полосы мягче, но эти два эффекта остаются. Если без чересполосицы таблица «разваливается» и строки трудно читать, значит, она плохо свёрстана.

7. **Обратная связь** — entry: https://ilyabirman.ru/reference/#feedback · серия из трёх статей «Расскажите об обратной связи в интерфейсе»: часть первая https://bureau.ru/soviet/20160823/, часть вторая https://bureau.ru/soviet/20160906/, часть третья https://bureau.ru/soviet/20160920/
   Часть первая (адекватность и нежность). Действия пользователя должны вызывать адекватную и заметную реакцию. Пример: электронная очередь на почте печатает номерок через две секунды после нажатия, и люди жмут повторно, потому что реакции нет. Хорошие примеры: подсветка ссылки и курсор-рука при наведении, оттяжка списка на айфоне, звук отправки письма, точки вместо символов пароля (видно, что ввод идёт), анимированный индикатор, а лучше индикатор с долей завершённости и оставшимся временем, смена кнопки при добавлении товара в корзину без перезагрузки страницы. Обратная связь не должна быть грубой: диалог на каждое добавление в корзину надоест, а окно с кнопкой «OK» вместо сообщения в строке состояния похоже на наказание. Иногда достаточно отсутствия положительной реакции вместо явной отрицательной (например, не подсвечивается область, куда нельзя бросить объект).
   Часть вторая (предотвращение и честность). Сообщение о том, что что-то не сработало, раздражает несвоевременностью: человек узнаёт об этом уже после действия. Хороший интерфейс предотвращает бесполезные и ошибочные действия: кнопку, которую нельзя нажать, отключают и показывают отключённой («Назад» без истории, «Поделиться» без выбранного файла, «Отправить» в форме, пока не заполнены поля). Чтобы не сообщать об ошибках, их исправляют автоматически или ставят маски, исключающие неверный ввод (в комментариях к статье предупреждают, что маски часто ломают вставку, отмену и навигацию, поэтому их нужно тщательно тестировать). Обратная связь не должна обманывать: нельзя рапортовать о выполнении, пока команда не выполнена (звук отправленного письма на айфоне до реальной отправки; уместнее индикатор отправки). На часах команду сразу подтверждают как принятую, чтобы человек мог опустить руку, а о неудаче сообщают в течение короткого времени.
   Часть третья (мгновенность, непрерывность, физичность). Хорошая обратная связь адекватна, нежна, мгновенна, непрерывна и физична. Если результат нельзя показывать по ходу движения, показывают приближённый сразу и заменяют точным потом (карта увеличивается по мере движения на уже загруженных данных, детали появляются позже). Слайдер даёт мгновенную и непрерывную обратную связь: эффект виден ещё до отпускания кнопки мыши, ждать «OK» не нужно; полоса прокрутки тоже слайдер. Калькулятор с полями и кнопкой «Рассчитать» заставляет отвечать на сложные вопросы до результата, хотя человеку нужно разобраться в многомерном мире вариантов; слайдеры с пересчётом на лету показывают, как величины связаны (диапазоны одних меняются при изменении других), а поля внутри слайдеров сочетают удобство с точностью. Реакция на действие имеет наивысший приоритет: айфон при запуске приложения сразу показывал заготовленный снимок экрана, а непрорисованная часть страницы шла шахматным узором, но точно за пальцем; искусственное замедление ради анимации (плавная смена цвета ссылки при наведении) — ошибка. Физичность (инерция прокрутки, «отпруживание» у края) создаёт иллюзию непосредственного взаимодействия: человек перестаёт воспринимать экран как устройство ввода.

8. **Обратимость** — entry: https://ilyabirman.ru/reference/#reversibility · article «Обратимость элемента интерфейса»: https://ilyabirman.ru/meanwhile/all/reversibility/
   Обратимость — свойство элемента: пользователь может в любой момент вернуть его в начальное состояние, а в общем случае свободно переключать между всеми состояниями. Хорошо спроектированные элементы обратимы. Необратимый пример: группа радиокнопок, где изначально ничего не выбрано; выбранное уже нельзя «развыбрать». В правильной радиогруппе всегда выбран ровно один пункт, в том числе в начальном состоянии. То, что для перехода дальше выбор обязателен, обратимость не отменяет: она относится к самому элементу, а не к окружающему интерфейсу; поле ввода не сопротивляется стиранию, даже если оно обязательное. Второй пример: красная рамка у пустого обязательного поля после ухода из него; вернуть поле в «чистое» состояние уже нельзя, а решением было бы плавное затухание рамки.

9. **Модальность** — entry: https://ilyabirman.ru/reference/#modalnost · серия из трёх статей «Что такое модальность и почему её принято ругать»: часть первая https://bureau.ru/bb/soviet/20160209/, часть вторая https://bureau.ru/soviet/20160223/, часть третья https://bureau.ru/soviet/20160308/
   Часть первая (что это). Жест — действие, которое человек не разделяет на составляющие. Один и тот же жест в разных состояниях интерфейса может значить разное (Энтер в редакторе и в чате). Интерфейс модален, если в нём есть состояния, которые человек не осознаёт во время жеста, но в которых жест трактуется по-разному; модальная ошибка — когда из-за этого получился не тот результат. Часть про «не осознаёт» важна: тап в левый нижний угол в приложении «Телефон» и в браузере ведёт в разные места, но модальности нет, потому что внимание занято задачей приложения; тап в привычный угол на не той странице домашнего экрана — модальность. Модальность — признак плохого интерфейса, а не рассеянности пользователя. Интерфейс может быть модален по отношению к одному жесту и немодален по отношению к другому, а в целом немодален только если немодален по всем жестам. Хуже всего, когда состояние меняется помимо воли пользователя (кнопка остановки загрузки за долю секунды до тапа превращается в «перезагрузить»).
   Часть вторая (заметность состояния как компромисс). Дизайнеры часто рассуждают так: раз дело в неосознании, сделаем состояние заметнее (выбранный инструмент Фотошопа меняет курсор; айфон трясёт иконки в режиме перетаскивания; цвет каретки показывает раскладку). Это снижает число ошибок, но у инструментов остаётся много невидимых состояний (твёрдость кисти, режим смешивания, слой). Автор называет это компромиссом: интерфейс «кричит» о своём состоянии, внимание переключается с задачи на состояние, и это мешает выработке привычки, а значит снижает эффективность.
   Часть третья (способы устранения). Лучше не привлекать внимание к состоянию, а проектировать интерфейс, где жесты работают одинаково во всех состояниях. Три способа. Первый: разделить жесты, например отдельные кнопки для фото и видео вместо одной кнопки, которая зависит от режима камеры; в картах масштаб колесом прокрутки разделил жесты внутри карты, но создал модальность на уровне страницы (колесо то прокручивает страницу, то меняет масштаб), настоящим решением стал двухпальцевый зум. Второй: квазирежимы, термин Раскина — состояние, которое пользователь удерживает физически (рация, сцепление, педаль отключения микрофона, зажатая кнопка мыши при перетаскивании; Шифт вместо Капслока; современные редакторы с модификаторами вместо режимов в «ви-ай»; зажатые клавиши лупы и руки в Фотошопе). Третий: изменить сценарий, например сначала выбрать письмо, потом нажать «удалить», вместо выбора инструмента «удалить», которым тыкают в письма. Универсального способа избавиться от модальности, по словам автора, пока нет.
